# RTLink overlay structure investigation

Direct byte inspection confirms that `assets/PRINCE.EXE` has a conventional MZ root image of 152,637 bytes, followed by 137,778 bytes of appended overlay material. The root ends at byte `0x2543d`; the first overlay relocation block begins at 152,640, after three zero padding bytes. The overlay descriptor table is located inside the root at decimal offset 150,347 (`0x24b4b`), and contains 16 records of 18 bytes, IDs 2 through 17. The earlier offset `0x24a8b` is 192 bytes before that table and is not its start.

Each descriptor decodes as `<HHHBBHHHHH>`: link segment, unknown word `f2`, relocation position in paragraphs, high relocation-position byte, flags, unknown word `f8`, relocation count, unknown word `fc`, overlay ID `fe`, and code size in paragraphs. The relocation byte offset is `(pos + hi*65536) * 16`. A relocation record is four bytes (`<HH>`: offset, segment). The relocation area occupies `ceil(nrel/4) * 16` bytes, so code starts at `relocation_offset + ceil(nrel/4)*16`; the code length is `size*16` bytes. For each relocation, the site inside code is `(rseg-link_segment)*16 + roff`. The published loader adds runtime load segment `0x0100` to the word at that site.

Concrete first entry (overlay 2): descriptor at 150,347; link segment `0x2344`; relocation position 152,640; flags 4; 821 relocations; ID 2; 1,675 paragraphs of code. Since `ceil(821/4)*16 = 3,296`, code starts at 155,936 and occupies 26,800 bytes, ending at 182,736, the next overlay's relocation area. The independently parsed table has 2,687 relocation records total; every relocation site is within its overlay code extent, and all overlay extents meet exactly.

The final row (overlay 17) begins its relocation block at 268,656; its 161 relocation entries occupy 656 padded bytes, so code begins at 269,312. The descriptor declares 1,319 paragraphs (21,104 bytes), ending at 290,416, while the physical file ends at 290,415. Both `PRINCE.EXE` and `PRINCE2.EX_` have this exact one-byte terminal shortfall. A real RTLink Plus 6.10 run through the local MS-DOS Player produced a small two-overlay executable from a Microsoft C 5.10 resident entry and two MASM far-return functions. Its table at offset 4,763 (`0x129b`) uses the same 18-byte record layout: overlay IDs 2 and 3, zero relocations, and one paragraph each, with file extents `[6496,6512)` and `[6512,6528)`. The MZ root ends at 6,487, leaving nine bytes before overlay data. Reproducible assembly/link sources and command details are in `evidence/rtlink-probe/README.md`; the output hash and exact descriptor values are in `evidence/rtlink-layout.json`.

The MSC 5.10 object requested `LLIBCE.LIB`, absent from the local installation. For this layout-only probe, the installed `LLIBCR.LIB` was copied under the expected name in the scratch directory, alongside RTLink 6.10's own `RTLUTILS.LIB`. The executable linked without diagnostics, but this alias is not evidence of a faithful runtime-library closure. The installed RTLink Plus 4.00 binary identifies itself as Version 4.00, and its bundled sample link log has the same banner. Attempts to run a comparable 4.00 response-file probe fell back to positional prompts and emitted no output, so the synthetic 4.00 case remains unresolved.

The linker runtime source distinguishes its own in-memory section metadata from these on-disk records. RTLink 4.00's `OVLMGR.ASM` defines a 16-byte `info_section` structure; the RTLink 6.10 source has a related but evolved manager structure. These are not the 18-byte descriptors stored in the executable.
